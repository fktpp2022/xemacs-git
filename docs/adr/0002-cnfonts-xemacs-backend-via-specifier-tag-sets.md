# cnfonts-xemacs backend: shim five GNU font calls onto specifier tag-sets

XEmacs has no Lisp fontset API and no `font-spec`/`set-face-attribute`/`face-attribute`/`x-list-fonts`/`set-fontset-font`; it selects a font **per charset** through face-font specifier tag-sets carrying charset predicates (`src/specifier.c:1230`, matched at `src/faces.c:1134`). We decided the `cnfonts-xemacs` compat layer overrides **exactly those five functions** and leaves every other cnfonts internal (profile loading, face selection, the English path that already works via `set-face-font 'bold …`) running untouched. For v1, `set-fontset-font` lowers to `(set-face-font FACE FONT 'global TAG-SET)` with the single built-in `two-dimensional` tag rather than per-script custom tags. Per-codepoint fidelity is the one accepted approximation: cnfonts's `(set-fontset-font "fontset-default" nil extb-fontspec nil 'prepend)` (EXT-B, `cnfonts.el:594`) has no XEmacs equivalent — no codepoint-range key, no fontset default bucket — so it collapses to a `(two-dimensional final)` fallback.

## Considered options

- **Per-script custom tags up front** (`define-specifier-tag` with a charset predicate per script, distinguishing han / kana / hangul / bopomofo / cjk-misc): deferred, not rejected. It buys fidelity cnfonts's common case does not need — Latin-plus-CJK is the whole of the milestone's success test — and costs a tag registry plus charset inventories before a single glyph has been rendered. Add when a rendering check shows the coarse tag is actually wrong, which is the same moment the hangul `append` fallback becomes worth expressing.
- **Widen the shim** beyond the five (e.g. shadow cnfonts's face-selection or profile logic): rejected. Every shadowed function is a divergence from upstream that must be re-audited on each cnfonts release; the research found only five calls with no XEmacs equivalent, so five is the whole surface.
- **Native reimplementation of cnfonts (β)** — the map's escape hatch if per-charset mapping proved infeasible: not taken. Per-charset selection is native and reachable from user Lisp (the repo's own `docs/user-config/xft-chinese-font-configuration.el` drives it), so upstream cnfonts can run behind a thin shim.
- **Cutting per-codepoint EXT-B out of scope**: rejected. Declaring it out of scope would delete a fallback that mostly works. Ext-B codepoints land in the 2D JIT charset `jit-ucs-charset-0`, so the `final`-stage fallback does render them — just with *any* CJK font the chinese font could not cover, not a codepoint-pinned extb font.

## Consequences

- Known ceiling, to be marked in code: the EXT-B path is a **final-stage fallback, not a codepoint-pinned default**. Two divergences from GNU, both benign for the milestone: priority is inverted (GNU makes extb the highest-priority default bucket, XEmacs the lowest-priority fallback — the same glyphs render either way, because common hanzi match at the `initial` stage and never reach `final`), and scope is broader (any uncovered 2D char falls to extb, not just Ext-B).
- Under the single coarse tag, cnfonts's `'hangul … 'append` fallback (`cnfonts.el:590`) is a no-op: a Chinese font lacking Korean glyphs has no per-script escape hatch. Same trigger as the per-script-tags upgrade above.
- `HOW-TO-ADD` maps cleanly: `prepend`/`append` pass through to `set-face-font`'s `how-to-add` argument (`src/specifier.c:2237`).
- The milestone's success test stays as written: a headless gate that the config code runs and mutates the right faces/charsets, plus a manual GUI check that CJK text renders aligned. Exact-Ext-B-font rendering is verified at that GUI check, not in CI.
